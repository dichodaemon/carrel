# Bootstrap Configuration File

## 1. Objective

Add a declarative configuration file that captures slot definitions and entry-to-slot mappings so that `carrel bootstrap` can recreate the full deployment topology on a fresh installation without manual `carrel slot add-entry` commands. A generation command produces the file from live registry state; bootstrap and register consumer apply it.

## 2. Scope

| In scope | Out of scope |
|---|---|
| Declarative file format for slots and entry mappings | Schema for entries themselves (already on disk) |
| `carrel bootstrap` and `carrel register consumer` reading and applying the file | Host-local bootstrap files |
| `carrel slot generate <consumer>` command to produce the file from registry state | Bidirectional sync (CLI slot commands updating the file) |
| Carrel-omp source's own consumer as first consumer | — |

## 3. Sources

1. **Carrel registry** — `/workspace/.carrel/registry` (slots, slot entries, consumers, sources)
2. **Source convention rules** — `carrel-omp:rule:carrel-configuration` and `internal/registry/schema.go`
3. **Existing slot mappings** — 6 slots on the `carrel` consumer: `APPEND_SYSTEM.md`, `carrel-configuration`, `grill-me`, `no-push-oh-my-pi`, `rebase-pr-chain`, `rebase-pr-tree`
4. **Entry compound IDs** — format `source-alias:type:name` (e.g., `carrel-omp:append-system:beads-policy.md`)

## 4. Approach

### 4.1. Ownership model

Slots belong to consumers in the registry schema. The declarative file matches this: it lives in the consumer, not the source. A source carries only entries — portable, topology-agnostic. The consumer declares which entries from which sources feed its slots. This eliminates ambiguity about cross-source slot composition.

### 4.2. File location

`<consumer-path>/.carrel/slots.yml` — one file per consumer. For the `carrel` consumer: `/workspace/carrel/.carrel/slots.yml`.

### 4.3. Format

YAML. Since the file is machine-generated by `carrel slot generate`, the format can be expressive. Entry references use full compound IDs (`source-alias:type:name`) — unambiguous across sources. Composed mode is per-entry.

```yaml
slots:
  - name: APPEND_SYSTEM.md
    dest: APPEND_SYSTEM.md
    compose: concat
    entries:
      - carrel-omp:append-system:APPEND_SYSTEM.md
        mode: concat
      - carrel-omp:append-system:beads-policy.md
        mode: concat
      - carrel-omp:append-system:carrel-policy.md
        mode: concat
      - carrel-omp:append-system:folio-policy.md
        mode: concat

  - name: carrel-configuration
    dest: rules/carrel-configuration.md
    compose: override
    entries:
      - carrel-omp:rule:carrel-configuration
        mode: override
```

**Entry reference fields:**

| Field | Required | Description |
|---|---|---|
| `ref` | Yes | Compound ID: `source-alias:type:name` |
| `mode` | No | Per-entry compose mode (`concat` or `override`). Defaults to the slot's `compose`. |

Compound IDs are serialized as a single field (`carrel-omp:append-system:beads-policy.md`) rather than structured `{ source, type, name }` — this keeps the file aligned with how identifiers appear in CLI output and `carrel inspect`.

### 4.4. Generation command

`carrel slot generate <consumer-alias>` reads the consumer's current registry state, collects all slots and their entry links, and writes `slots.yml` to `<consumer-path>/.carrel/slots.yml`. The file includes every slot and every entry link — a full snapshot of the consumer's deployment topology. Re-running is idempotent.

### 4.5. Bootstrap integration

When `carrel bootstrap` runs:
1. Register universal sources first (`carrel-omp`). Their entries must exist in the registry before any consumer reads `slots.yml`.
2. Register consumers. For each consumer with `.carrel/slots.yml`: create the declared slots if missing, link all declared entries by their compound IDs. Entries referencing non-universal sources may not yet exist — those are skipped with a warning.
3. Skip if slot or entry link already exists (idempotent).

`carrel register source <alias> --consumer=<c>` also applies the consumer's `.carrel/slots.yml` after linking the source. This catches entry references that were skipped during bootstrap because the source hadn't been registered yet. The `carrel run` warning (section 4.6) covers any remaining gaps.

### 4.6. Consistency checking at `carrel run`

`carrel run` reads the consumer's `.carrel/slots.yml` and cross-references it against the live registry. For each entry declared in the file that has no corresponding slot link in the registry, it emits a warning. Deployment proceeds — the warning is a reminder, not a block.

This catches the case where a consumer was cloned with a `slots.yml` but its sources haven't been registered yet (e.g., after a fresh clone before `carrel bootstrap` or `carrel register source`). The user re-runs the missing registration command, and the warning disappears.

`carrel plan` also performs this check, giving the same warning during the preview pass.

### 4.7. Separation of concerns

| Concern | Where |
|---|---|
| Entry content | Source files on disk |
| Entry registration | `carrel config scan <source>` |
| Slot definitions | `.carrel/slots.yml` (consumer) |
| Slot-to-entry links | `.carrel/slots.yml` (consumer) |
| Live registry state | `/workspace/.carrel/registry` (Dolt) |

`slots.yml` is a snapshot — `carrel slot generate` captures current state. `carrel bootstrap` and `carrel register consumer` replay it. The registry remains the live system of record; the file is the portable declaration.

## 5. Constraints

- **YAML only.** No JSON, no TOML. One format keeps parsing simple.
- **Consumer-scoped.** One `slots.yml` per consumer. Entries reference sources freely — cross-source composition is natural.
- **Idempotent.** Re-running bootstrap, register source, or generate must not duplicate slot entries.
- **Backward compatible.** Consumers without `.carrel/slots.yml` use convention-based default slot generation via `carrel register source`.

## 6. Open Questions

1. Should `carrel slot add/rm` commands also update `slots.yml`? Out of scope for v1. The file is machine-generated via `carrel slot generate`. CLI slot commands modify the registry directly; re-running generate captures the new state. Bidirectional sync is a separate feature.

2. Should `carrel slot generate` show a diff before overwriting `slots.yml`? Yes — a `--diff` flag or default diff output would prevent surprises. Without it, generate is a blind overwrite.

3. Should `carrel register source` warn if the consumer's `slots.yml` references entries that don't yet exist (source not yet registered)? Yes — a warning rather than an error, since source registration order is arbitrary during bootstrap.
